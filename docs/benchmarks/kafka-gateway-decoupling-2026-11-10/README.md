# Kafka 网关回复消费与转发完成解耦实验

## 实现与边界

候选只将网关的远程批转发完成从回复消费 worker 中分离。worker 完成路由校验和入队后即可处理下一条记录，发送完成回调再向消费循环提交 completion。总未提交记录仍受原 completion window 限制，offset 只能越过连续成功或终态过期的记录；取消、失败和分区空洞仍阻止不当提交。

转发条目由发送方与入队方共同持有，双方完成后才清理回调、context 和借用数据并回池；关闭时先停止 worker，再等待未完成回调。瞬时错误才进入等待重试路径，数量同样受 completion window 限制。本地交付、非批转发和请求发布确认路径保持原语义。

## 同条件对照

总并发 1280、默认 GC，应用 4 CPU / 1 GiB、Kafka 2 CPU / 3 GiB，其余参数与 [并发测量](../kafka-gateway-2026-11-09/README.md) 一致。基线网关、候选网关、基线直读、候选直读正反序各一轮，每轮 30 秒，新 Broker 与独立预热。版本由 version.json 标识，不以仓库 HEAD 代替源码快照。

| 版本 | 模式 | RPC/s | p99 ms | CPU µs/RPC |
|---|---|---:|---:|---:|
| base | thrift | 134860 | 20.35 | 22.60 |
| base | direct | 145622 | 18.45 | 19.02 |
| candidate | thrift | 131186 | 21.05 | 22.78 |
| candidate | direct | 145813 | 18.40 | 19.08 |

候选网关相对基线吞吐变化 -2.72%，p99 增加 0.70ms；直读变化 0.13%。基线网关相对直读低 7.39%，候选低 10.03%。

每次转发的平均消息数从 19.39 增至 22.85，但没有带来端到端收益。这组数据不支持采用该候选，保留基线；不据此断言所有解耦方案都无效。全部八轮零调用失败、应用测量期限流次数为零，其他容器采样峰值最高 0.0858 核。未将无收益候选升级为持续负载版本。

## 文件与复现

`rounds.json` 为全部原始数值，`comparison.csv/json` 为两轮汇总，`version.json` 给出基线与候选二进制指纹、基线源码清单和变化文件指纹。`candidate.patch` 是相对该基线快照的实验补丁，不是当前实现的默认改动。

使用与基线清单匹配的源码，在独立副本应用补丁后构建 Linux ARM64 的 examples 测试二进制。基线和候选均执行 TestKafkaLoadCurve，参数沿用并发测量说明，将总并发固定为 1280；分别设置 REPLY_MODE=thrift/direct。比较每种版本/模式的两轮均值，保留原始错误、环境和资源采样；不能用此实验的样本替代新的测量。

## 正确性验证

Kafka 模块 race 和新增的异步提交空洞、迟到完成、回调释放、重试、过期及取消用例通过。真实 Kafka 的回复失败重投、重连 offset、路由扩容/重启（batch 0/32）和提交顺序/再均衡通过。

公共合约的 DeadlineCancellationAndLateReply 在首次完整运行中超时。随后用相同条件对基线和候选各执行两次该用例，两者均首次在 `contract.go:230` 遇到 `COORDINATOR_LOAD_IN_PROGRESS`，第二遍通过。这是两版共有的冷启动失败模式，不作为候选独有回归，也不据此宣称全部合约通过。未修改测试断言、超时或跳过设置。完整结论见 validation.json。
